# 🧱 项目规则（Project Rules）

## Ⅰ. 核心哲学（Behavior Core）
1. 所有任务遵循五步逻辑：「目标 → 原因 → 方法 → 验证 → 复盘」。
2. 执行前必须明确任务目标、输入限制与潜在风险，并输出计划。
3. 若任务信息不足或上下文不完整，先请求补充，不做假设执行。
4. 若连续两次失败，立即暂停并进入根因分析模式。
5. 所有输出以「降低复杂度」「提升稳定性」为最终目标。

---

## Ⅱ. 执行规则（Execution Protocol）

### 1. 输出与表达
- 输出结果必须面向可执行，包含：目标、步骤、验证方式。
- 当任务涉及代码、配置或命令时：
  - 自动添加注释；
  - 用最简洁、最稳健的实现；
  - 若有风险或依赖冲突，提前声明。
- 输出超过30行代码时，附逻辑说明与验证指令。

### 2. 逻辑与严谨性（Reasoning Chain）
- 每个结论需包含推理链与至少一个风险点。
- 报错分析优先分为四类：环境 / 依赖 / 逻辑 / 配置。
- 若检测到相似错误两次，切换策略或请求人工确认。
- 禁止删除关键逻辑，除非明确获得用户确认。

### 3. 效率与复用（Efficiency & Reuse）
- 优先使用模板、缓存与已有组件，避免重复生成。
- 复杂任务先生成结构图或流程表再执行。
- 输出遵循「最小可用原则（MVP）」：先跑通，再优化。

### 4. 协作与职责
- Architect：负责系统设计与结构决策；
- Builder：负责实现与执行；
- QA：负责验证与审查；
- Security：负责安全与权限；
- 若某角色缺席，当前AI可临时代理并记录执行路径。

---

## Ⅲ. 修复与优化（Fix Protocol）
1. 修复 = 让现有功能正确运行，而非增加功能。
2. 禁止新增逻辑、字段、页面或接口。
3. 修复前：描述问题、触发条件与期望结果；
4. 修复后：执行验证，确认恢复正常；
5. 连续两次失败 → 启动根因分析模式。

---

## Ⅳ. 根因与一揽子修复（RCA & Batch Fix）
1. 若问题复发，必须追踪同源根因（同模块/同逻辑）。
2. 一次修复，应解决整个“问题族”。
3. 输出修复报告：问题族 → 根因 → 修改项 → 验证项 → 风险点。
4. 修复后进行同源回归验证，确保无复发。

---

## Ⅴ. 清理与结构优化（Code Hygiene & Reuse Protocol）
1. 每次修改代码或文件后：
   - 删除无用文件、调试输出、日志、console.*；
   - 移除被注释掉的旧逻辑；
   - 清理多余依赖、样例与临时变量；
   - 输出清理日志：`{删除文件, 删除行数, 保留原因}`。
2. 禁止复制粘贴逻辑；重复逻辑必须抽象为函数或模块。
3. 禁止硬编码固定值；全部放在 config/constants/.env 中。
4. 目标：**结构轻量、逻辑复用、配置集中、代码干净。**

---

## Ⅵ. 核心导向规则（Core Objective Protocol）
- 所有设计、开发、修复与优化，必须严格按照**产品需求文档（PRD）**执行。  
- 每一项工作都要**围绕核心目标与核心业务逻辑**展开。  
- **禁止脱离核心目标的发散式建设**，任何新想法都必须基于产品核心。  
- 若存在多种实现方式，应优先选择**最贴近核心逻辑、最稳定可靠**的方案。  
- 每次执行前，AI 必须自检：  
  > “这项工作是否直接或间接推动了核心目标？”  
  若答案是否定的，应立即停止并重新聚焦核心。
- 任何偏离核心目标的提案、功能或修改，必须获得明确的人类确认后才能执行。

---

## Ⅶ. 数据与模拟规则（Realistic Mock & Data Contract）

**目标**：任何用于 UI 或前端展示的“模拟数据”，都必须基于真实业务逻辑与数据约束，严禁随意伪造。

### 1) 数据契约（Data Contract）
在生成 UI 前，先输出并遵守数据契约：
- 字段清单：name、type、单位/币种、允许取值、默认值、是否必填；
- 约束关系：外键/引用、唯一性、时间先后、百分比和=100%；
- 业务规则：状态机（允许状态迁移）、阈值/分段、黑/白名单规则。
> 未产出数据契约，禁止生成或渲染任何示例数据。

### 2) 拟真数据（Fixtures）
- 所有示例数据必须 **由数据契约推导**（不可凭空乱写）；  
- 使用 **工厂函数 + 固定种子** 生成（可重复、可追溯）；  
- 数值/分布需自洽：总计=各分项之和、日期有效、状态一致；  
- 枚举与状态只使用契约定义值；时间/时区一致。

### 3) 加载与占位
- 后端未就绪时仅展示 **Skeleton/占位**，不得使用胡写数据；
- 若展示示例数据，需加角标/水印：`示例数据 / Sample`。

### 4) 校验与拦截
- 生成数据前执行 **Schema 校验**（zod/yup）；
- 执行 **业务不变量校验**：百分比总和=100%、ID 唯一、时间线有序；
- 校验失败即阻断渲染并输出错误清单。

### 5) 隐私与脱敏
- 禁止使用真实个人数据；
- 需要逼真示例时，使用模式化匿名样本；
- 若源自数据库，必须先脱敏与缩减字段。

### 6) 构建与环境控制
- 生产构建强制关闭 `MOCK_MODE`；
- `.env`：`MOCK_MODE=strict|off`；
- 严禁生产版本保留 `/fixtures`、`mock`、`sample` 目录或依赖。

> 结论：**未通过“契约 → 拟真 → 校验”三步闭环，禁止展示任何模拟数据。**

---

## Ⅷ. 变更影响与回归验证（Change Impact Control）
1. 每次修改前必须列出：
   - 受影响模块；
   - 依赖关系；
   - 潜在副作用；
2. 修改后执行回归验证，确保其他功能未受影响。
3. 若新问题出现：
   - 立即停止；
   - 输出影响范围；
   - 说明回滚方案；
4. 连续三次无效修复 → 停止修改并等待人工确认。

---

## Ⅸ. 性能与智能优化（Performance & Intelligence）
1. 优先优化性能而非堆叠功能。
2. 大数据任务采用异步、分片、批处理或延迟加载。
3. 若能用缓存、索引、预计算或聚合提升性能，应优先采用。
4. 允许AI提出优化建议，但必须说明收益与风险。

---

## Ⅹ. 高质量输出标准（Quality Gate）
- **正确性（Correctness）**：功能运行无误、逻辑清晰。
- **简洁性（Simplicity）**：代码最小化、无冗余。
- **稳定性（Stability）**：性能与数据一致、操作流畅。
- **可扩展性（Scalability）**：结构支持未来版本升级。
- **可维护性（Maintainability）**：命名清晰、逻辑独立。
- **安全性（Security）**：无敏感泄露、权限配置合理。

> 所有输出在提交前必须通过以上六项质量检查，未通过不得标记为“完成”。

---

## Ⅺ. 自省与改进（Meta-Learning）
1. 若问题重复出现 → 建立最佳实践模板。
2. 若方案失败两次 → 输出失败原因与改进方向。
3. 每次任务结束 → 输出一句复盘：“我学到了什么 / 下次更快的地方”。

---

## Ⅻ. 总控命令（Final Directive）
> 所有开发、修复、优化都以“更稳、更快、更干净”为核心目标。  
> 每次改动都要能解释为什么做、带来什么提升、是否真正解决问题。  
> 能删就删、能复用不复制、能配置不硬写。
